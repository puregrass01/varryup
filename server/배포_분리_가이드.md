# VERY UP 서버 — 공개/내부 2프로세스 분리 배포 가이드

대상: 운영자(서버에 SSH 로 들어가 작업하는 사람)
근거: `보안감사_2026-09-16.md` 3절 (b) "표면 분리" + 4-3 "배포는 2단계로 나눈다"
전제: EC2 **한 대**, 인프라 추가비용 0원. 서버를 새로 사는 일이 아니다.

## 0. 한 장 요약

지금까지는 프로세스 **하나**가 인터넷에 열린 채로 `/privacy`(공개 필수)와 `/keys`(인증키 금고)를
동시에 서빙했다. 그래서 `/login` 무차별 대입, 직원 토큰 전량 덤프, 세션 탈취, 프록시 릴레이 남용이
전부 "인터넷에서 그 포트에 닿을 수 있다"는 한 가지 전제 위에 얹혀 있었다.

분리의 요점은 그 결함들을 하나씩 고치는 것이 아니라 **인터넷에서 도달할 수 없게 만드는 것**이다.

| | 공개 프로세스 | 내부 프로세스 |
|---|---|---|
| 진입점 | `serve_public.py` | `serve_internal.py` |
| 도달 경로 | 인터넷 → nginx(443) → 127.0.0.1:8080 | WireGuard(10.8.0.0/24) → 10.8.0.1:8001 |
| 경로 | `/privacy`, `/privacy/en`, `/ebay/deletion`(GET+POST), `/ebay/auth/accepted`·`/declined` | `/login`, `/`, `/staff`, `/keys`, `/logs`, `/licenses`, `/usage`, `/password`, `/api/*`, 프록시 릴레이 4종, `/proxy/health`, `/updates`, `/deletions` |
| admin.db | **없음** | 있음 |
| KEY_MASTER / ADMIN_SECRET | **없음** | 있음 |
| 세션·로그인 | **없음** | 있음 |
| 자체 상태 | `EBAY_QUEUE_DIR` 안의 큐·영수증·격리 파일뿐 | admin.db |
| OS 계정 | `veryup-public` | `veryup` |

**연결 방향은 내부 → 공개 읽기 한 방향뿐이다.** 내부 프로세스가 공개 프로세스의 큐 **파일**을
직접 읽는다(네트워크 호출이 아니다). 공개 → 내부 방향의 포트·라우트·소켓은 하나도 만들지 않는다.
여기서 방향이 뒤집히면 분리는 그 순간 무의미해진다.

> **프록시 릴레이는 왜 EC2 에 남는가**
> 쿠팡·네이버가 허용목록에 등록해 둔 것은 **EC2 의 아웃바운드 IP** 다. 릴레이를 사무실 LAN 으로
> 옮기면 마켓플레이스 허용목록을 전부 재등록해야 한다. 그래서 내부 프로세스도 EC2 에 두고,
> **인바운드만** WireGuard 뒤로 숨긴다. 사무실 공인 IP 는 유동이라 인바운드 IP 허용목록은 쓸 수 없다.

## 1. 필수 환경변수 전체 목록

두 유닛의 `EnvironmentFile` 을 **반드시 따로 둔다.** 하나를 공유하면 공개 프로세스에 `KEY_MASTER` 가
들어가고, 그 순간 "공개 쪽에는 키가 없다"는 전제가 통째로 무너진다.
(`serve_public.py` 는 그 상황을 감지해 **기동을 거부한다** — `PUBLIC_STRICT` 는 이제 기본이 on 이다.)

| `VERYUP_ENV` | ✕ | 공개 프로세스는 비밀값을 안 쓰므로 무관(`config.py` 는 여기 import 되지도 않는다) |

| `PRIVACY_OFFICER` / `PRIVACY_OFFICER_EN` | 권장 | PIPA 는 보호책임자 **성명(또는 직위)** 과 연락처를 요구한다. 미설정이면 일반 문구만 나가 기재사항이 불완전하다 |

| `PUBLIC_HOST` / `PUBLIC_PORT` | 선택 | `python serve_public.py` 로 직접 띄울 때만. systemd 는 uvicorn 인자를 쓴다 |
| `LOG_LEVEL` / `LOG_FILE` | 선택 | 기본 INFO / 미설정(journal 만). `LOG_FILE` 을 주면 10MB×3 회전 파일도 함께 남는다 |

**공개 프로세스에 절대 넣지 마라:** `KEY_MASTER`, `ADMIN_SECRET`, `BOOTSTRAP_ADMIN_USER`,
`BOOTSTRAP_ADMIN_PW`, `UPDATE_TOKEN`, `STAFF_PLATFORMS`.

### 1-2. 내부 프로세스 (`/etc/veryup/internal.env`, 권한 0600)

| 변수 | 필수 | 값·설명 |
|---|---|---|
| `VERYUP_ENV` | ✅ | `production`. **미설정이거나 오타면 내부 프로세스가 아예 뜨지 않는다**(`InternalStartupError`). 로컬 개발은 `VERYUP_ENV=development` 라고 **명시**해야 한다 — 모드를 추측하지 않는 것이 요점이다.<br>철자 그대로여야 한다: `prod`·`Production ` 같은 값은 개발 모드로 읽히므로 거부한다 |
| `ADMIN_SECRET` | ✅ | 세션·API 토큰 **서명** 전용 키. **32자 이상**이고 `KEY_MASTER`·`server/secret.key` 의 내용과 **달라야** 한다. ⚠ 이 두 검사는 `VERYUP_ENV` 와 무관하게 **개발 모드에도** 적용된다(`config._validate_admin_secret`) — 어기면 `SecretConfigError` 로 기동 거부. 생성: `python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `KEY_MASTER` | ✅ | 인증키 Fernet **암호화** 전용 키(44자 urlsafe base64). **기존 데이터를 계속 읽으려면 현재 `server/secret.key` 의 내용을 그대로** 넣는다. 새로 만들면 기존 암호문은 영구 복호화 불가 → 3-2 의 회전 절차를 그대로 따를 것 |
| `VERYUP_KEY_ROTATION` | 회전 중에만 | `1` 이면 **마스터 키 카나리아 실패가 기동을 막지 않는다**(ERROR 로그 + 기동 요약 경고 + 관리 화면 보라색 배너로 낮춘다). `KEY_MASTER` 를 실제로 회전할 때 **반드시 필요하다** — 새 키로 띄우는 순간 `admin.db` 에는 옛 키로 암호화된 행만 남아 카나리아가 실패하고, 그대로 막으면 재입력 화면(`/keys`)에 도달할 방법이 없다(3-2 참고).<br>이 변수가 여는 것은 **그것 하나뿐**이다 — 비밀값 존재·길이·동일값 검사와 파일 폴백 차단은 그대로다. `VERYUP_ALLOW_DEV_SECRETS` 로 대신하지 마라(그쪽은 폴백 전체를 연다).<br>⚠ **회전이 끝나면 반드시 제거하고 재기동**한다. 남겨 두면 다음 사고(`KEY_MASTER` 오타·롤백)가 조용히 통과한다 |
| `COMPANY_NAME` / `CONTACT_EMAIL` / `DATA_RETENTION` | ✅ | ⚠ **내부에도 필요하다.** `app.py` 가 `/updates` 때문에 `public.py` 를 import 하고, `public.py` 는 **import 시점에**(`public.py:169`) 이 3개를 검사해 `RuntimeError` 로 죽인다 — `PUBLIC_STRICT` 와 무관하다. 공개 쪽과 같은 값을 넣으면 된다 |
| `BOOTSTRAP_ADMIN_USER` | 최초 1회 | 계정이 0개일 때만 쓰인다. `admin` 같은 뻔한 이름은 피하라 |
| `BOOTSTRAP_ADMIN_PW` | 최초 1회 | **12자 이상**(미만이면 생성 거부). 생성된 계정은 `must_change_password=1` — 첫 웹 로그인에서 반드시 바꿔야 하고, 바꾸기 전에는 앱 `/api/login` 이 403 이다 |
| `STAFF_PLATFORMS` | ✅ | `role='staff'` 가 `/api/credentials` 로 받을 수 있는 플랫폼. 기본값은 **빈 집합**이라 설정하지 않으면 직원 앱이 인증키를 하나도 못 받는다. 예: `coupang,naver` |
| `UPDATE_TOKEN` | 자동 업데이트를 쓰면 ✅ | 미설정이면 `/updates` 라우트를 **등록하지 않는다**(404). ⚠ 서버와 Electron 클라이언트(`src/main_process.js` 의 `process.env.UPDATE_TOKEN`)를 **반드시 같은 값으로 함께** 설정하라. 한쪽만 켜면 전 직원 자동 업데이트가 조용히 401 로 죽는다 |
| `SESSION_HTTPS_ONLY` | 상황에 따라 | 운영 모드 기본 `True`. **WireGuard 위에서 평문 http 로 서비스한다면 `0` 으로 내려야 로그인이 된다**(Secure 쿠키를 브라우저가 보내지 않음). 이 구성에서는 VPN 이 암호화를 담당한다 |
| `EBAY_QUEUE_DIR` | ✅ | **공개 프로세스와 글자 그대로 같은 값**(대소문자·끝 슬래시까지). 다르면 `/deletions` 화면에 "큐 파일이 아직 없습니다"만 뜨고, 격리 본문 열람도 빈손이 된다. 예: `/var/lib/veryup`. 영속 경로여야 하고 `ReadWritePaths` 에도 같은 값이 있어야 한다(4-1 주석) |
| `EBAY_QUEUE_DB` / `EBAY_RECEIPT_LOG` | 선택 | 개별 경로를 따로 지정했다면 **공개 쪽과 똑같이** 여기도 지정한다 |
| `VERYUP_FORCE_ADMIN_PW_CHANGE` | 상황에 따라 | `1` 이면 기동 시 **활성 관리자 전원**에게 `must_change_password` 를 건다. 기존 `admin.db` 를 그대로 들고 넘어올 때 **딱 한 번** 쓰고 지운다(남겨 두면 재기동마다 다시 걸린다). 3-3 참고 |
| `VERYUP_ADMIN_PW_ACK` | 선택 | 비밀번호를 확인한 관리자 아이디 목록(쉼표 구분). 그 계정은 기동 경고·화면 배너에서 빠진다. 새 계정이 생기면 경고가 다시 뜬다 |
| `INTERNAL_ALLOWED_HOSTS` | 권장 | Host 헤더 허용목록(심층 방어). 예: `10.8.0.1,admin.internal,localhost` |
| `INTERNAL_ENABLE_DOCS` | 선택 | 기본 꺼짐. `1` 이면 `/docs`·`/redoc`·`/openapi.json` 을 되살린다(권장하지 않음) |
| `API_TOKEN_MAX_AGE_HOURS` | 선택 | 앱 베어러 토큰 수명(기본 168 = 7일). 짧게 줄일 수 있는 레버 |
| `UPDATE_DIR` | 선택 | 업데이트 파일 디렉터리(기본 `server/updates`) |
| `INTERNAL_HOST` / `INTERNAL_PORT` | 선택 | `python serve_internal.py` 로 직접 띄울 때만. `0.0.0.0` 은 거부한다 |
| `FORWARDED_ALLOW_IPS` | 구성에 따라 | 신뢰 프록시 IP. **`*` · `0.0.0.0/0` · `::/0` 은 기동 거부한다.**<br>(A) WireGuard 직결이면 **비워 둔다**(그리고 `--proxy-headers` 도 쓰지 않는다).<br>(B) 같은 호스트 nginx 뒤면 `127.0.0.1`.<br>왜 거부하나: 이 값이 `*` 면 누구나 `X-Forwarded-For` 를 지어내 **로그인 IP 잠금을 우회**하고 `login_logs.ip`·`key_access_logs.ip` 를 위조할 수 있다(감사 추적 오염). 4-2 참고 |
| `LOG_LEVEL` / `LOG_FILE` | 권장 | `LOG_FILE=/var/log/veryup/internal.log` 를 주면 로그인 잠금·권한 거부 경고가 파일로 남는다 |
| `VERYUP_ALLOW_DEV_SECRETS` | ✕ | 로컬 개발 전용 탈출구(비밀값 파일 폴백·자동 생성을 통째로 연다). **운영에는 절대 넣지 마라.** 키 회전 때문에 이 변수가 필요해 보인다면 그건 `VERYUP_KEY_ROTATION` 의 자리다 |

## 2. OS 계정과 파일 권한

공개 프로세스가 `admin.db` 를 **읽을 수조차 없게** 만드는 것이 이 절의 목적이다.
코드가 읽지 않더라도, 읽을 수 있는 권한으로 인터넷에 열린 프로세스를 돌리면
그 프로세스의 취약점 하나가 곧 인증키 DB 유출이 된다.

```bash
sudo useradd -r -s /usr/sbin/nologin veryup          # 내부
sudo useradd -r -s /usr/sbin/nologin veryup-public   # 공개
sudo groupadd veryup-queue
sudo usermod -aG veryup-queue veryup
sudo usermod -aG veryup-queue veryup-public

# 코드
sudo chown -R veryup:veryup /opt/veryup/server
sudo chmod 750 /opt/veryup/server
sudo setfacl -m u:veryup-public:rx /opt/veryup/server          # 공개도 코드는 읽어야 한다
sudo setfacl -R -m u:veryup-public:r /opt/veryup/server/*.py

# 인증키 금고 — 내부 계정만
sudo chown veryup:veryup /opt/veryup/server/admin.db
sudo chmod 600 /opt/veryup/server/admin.db
# secret.key 는 KEY_MASTER 로 옮긴 뒤 서버에서 지운다(3-2 참고)

# eBay 큐 — 공개가 쓰고, 내부가 읽고 상태만 갱신한다
# ⚠ 이 디렉터리가 EBAY_QUEUE_DIR 이며, admin.db 가 있는 디렉터리와 **반드시 달라야** 한다.
#    같으면 공개 프로세스가 admin.db 를 지우거나 갈아치울 수 있는 쓰기 권한을 갖게 되고,
#    serve_public.py 가 그 상황을 감지해 기동을 거부한다.
sudo mkdir -p /var/lib/veryup
sudo chown veryup-public:veryup-queue /var/lib/veryup
sudo chmod 2770 /var/lib/veryup        # setgid: 새로 생기는 파일이 veryup-queue 그룹을 상속
# (공개 유닛의 UMask=0007 과 함께 쓰면 큐 파일이 0660 으로 생성된다)
# 이 디렉터리에는 거절된 알림의 **원본 본문**(eBay userId 포함)도 격리 파일로 쌓인다.
# 그래서 o+rwx 를 주지 않는다 — 2770 이 최대치다.
# ⚠ 영속 경로여야 한다. /tmp·/run 이나 tmpfiles 자동 청소 대상에 두지 마라 —
#    런타임에 이 디렉터리가 사라지면 ebay_queue 가 자가 복구하지 않고,
#    알림 적재와 거절 감사기록이 조용히 빈다(밖에서 보이는 응답은 정상이라 아무도 모른다).
systemd-tmpfiles --cat-config | grep -n '/var/lib/veryup' || echo "청소 규칙 없음 ✅"

sudo mkdir -p /var/log/veryup && sudo chown veryup:veryup /var/log/veryup
```

> **큐 파일의 주인은 공개 프로세스다.** 내부 프로세스는 큐 파일이 없을 때 **만들지 않는다**
> (만들면 소유자가 내부 계정이 되어, 공개 프로세스가 알림을 받는 순간 쓰기 실패로 그 알림을 잃는다).
> `/deletions` 화면에 "큐 파일이 아직 없습니다"가 보이면 공개 프로세스를 먼저 띄우거나
> 두 유닛의 `EBAY_QUEUE_DIR` 값이 같은지 확인하라.

## 3. 마이그레이션 — 기존 단일 프로세스에서 넘어갈 때

> # ⛔ 기존 `admin.db` 를 그대로 들고 넘어온다면, 다른 무엇보다 먼저 **관리자 비밀번호를 바꿔라.**
>
> 기본계정 자동 생성을 막은 것은 **새로 만드는 경로**뿐이다. **이미 `admin.db` 안에 있는 계정은
> 그대로 유효하고, 로그인도 그대로 된다.** 감사가 지적한 그 `admin / admin1234` 가 바로 이것이다.
> `must_change_password` 열은 나중에 `DEFAULT 0` 으로 추가됐기 때문에 기존 계정은 전부
> '강제 변경 대상 아님'으로 시작한다 — 즉 **아무도 비밀번호를 바꾸지 않아도 아무 일도 일어나지 않는다.**
>
> 내부 프로세스는 이제 기동할 때마다 그런 계정을 세어 **경고 블록**을 남기고
> (`⚠ 비밀번호를 **확인했다고 표시되지 않은** 활성 관리자 계정 N개: ...`),
> 관리 화면 상단에 **빨간 배너**를 띄운다. 조치는 3-3 을 보라.

### 3-1. 순서를 지켜야 하는 이유

키 회전은 **순서를 뒤집으면 복구가 불가능하다.** `KEY_MASTER` 를 먼저 바꾸면 저장된 암호문을
읽을 수 없게 되고, 그때는 원본(마켓플레이스 쪽 값)도 이미 폐기된 뒤일 수 있다.

> **`KEY_MASTER` 를 진짜로 바꾸는 경우에는 `VERYUP_KEY_ROTATION=1` 이 필수다.**
> 새 키로 띄우는 순간 `admin.db` 에는 아직 **옛 키로 암호화된 행**만 있으므로 기동 시 마스터 키
> 카나리아가 실패한다. 그 상태로 기동을 막으면 인증키를 재입력할 `/keys` 화면 자체가 뜨지 않아
> **회전이 구조적으로 불가능**해진다(예전에는 그 오류 메시지가 "새 KEY_MASTER 로 기동 →
> /keys 에서 재입력"이라고, 방금 자기가 막은 단계를 안내하는 순환이었다).
> 이 변수는 **카나리아 실패를 경고로 낮추는 것 하나만** 한다 — 비밀값 존재·길이·동일값 검사는
> 그대로 살아 있다. `VERYUP_ALLOW_DEV_SECRETS` 를 대신 쓰지 마라(그쪽은 비밀값 파일 폴백과
> 자동 생성까지 통째로 여는 로컬 개발 스위치이고, 이 가이드가 "운영에 절대 넣지 마라"로 못박은 값이다).
>
> **`KEY_MASTER` 를 바꾸지 않는 이사(기존 `secret.key` 내용을 그대로 주입)라면 이 변수는 필요 없다.**
> 필요해졌다는 것은 곧 "지금 넣은 키가 이 `admin.db` 의 키가 아니다"라는 뜻이니, 회전 의도가
> 아니었다면 **띄우지 말고 키부터 확인하라.**

### 3-2. 절차

0. **시작하기 전에 — `admin.db` 를 백업하고, 정말 회전이 필요한지 먼저 확인한다.**

   ```bash
   sudo systemctl stop veryup-internal
   sudo cp -a /path/to/server/admin.db /path/to/backup/admin.db.$(date +%Y%m%d-%H%M%S)
   ```

   카나리아가 실패했다고 해서 항상 "키가 바뀐" 것은 아니다. **훨씬 흔한 원인은 오타다** —
   `KEY_MASTER` 를 복사하다 앞뒤 공백이 붙거나, 끝의 `=` 가 빠지거나, 옛 값으로 롤백된 경우다.
   그 상태에서 4-A(재입력)로 들어가면 **멀쩡한 인증키를 스스로 지우게 된다.**

   회전을 시작하기 전에 이 순서로 확인하라:
   1. `internal.env` 의 `KEY_MASTER` 가 `server/secret.key` 의 내용과 같은가? (같다면 오타가 아니라 진짜 회전이다)
   2. 값에 따옴표·공백·줄바꿈이 섞이지 않았는가? (`cat -A` 로 보면 드러난다)
   3. 옛 `secret.key` 백업이 남아 있는가? 남아 있다면 그 값으로 한 번 띄워 보라 —
      카나리아가 통과하면 **회전이 아니라 설정 오류**였던 것이고, 4-A 는 필요 없다.

   이 단계를 건너뛰고 지운 인증키는 되돌릴 방법이 없다(그래서 백업이 먼저다).

1. **마켓플레이스 쪽 자격증명을 먼저 재발급한다.**
   쿠팡 accessKey/secretKey 재발급, 네이버·ESM·아임웹 비밀번호 변경.
   근거: `secret.key` 와 `admin.db` 가 같은 디렉터리에 있었고 그 디렉터리가 Google Drive 동기화를
   타고 개인 PC 까지 따라왔다(감사 §5). **이미 노출된 것으로 간주한다.**
2. **`ADMIN_SECRET` 을 새로 만든다.** (`secrets.token_urlsafe(32)`)
   이 값을 새로 넣는 순간 기존 세션·API 토큰이 **전부 무효화된다.** 직원 재로그인이 필요하다.
   서명키와 암호화키를 분리했기 때문에, 이제 암호문을 잃지 않고 이 회전이 가능하다.
3. **`KEY_MASTER` 를 정한다.**
   - 기존 인증키를 그대로 읽으려면 → 현재 `server/secret.key` 의 **내용을 그대로** 넣는다.
     (이 경우 4-B 로 건너뛴다 — `VERYUP_KEY_ROTATION` 은 넣지 않는다.)
   - 키까지 회전하려면 → 새 Fernet 키를 만들고 4-A 로 간다. 인증키는 **전부 재입력**해야 한다.
     ```bash
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
4. **내부 프로세스를 띄운다.** 3에서 고른 쪽에 따라 절차가 갈린다.

   **4-A. 키를 회전하는 경우 — 회전 모드로 띄우고 재입력한다.**

   ```bash
   # internal.env 에 새 KEY_MASTER 를 넣고, 회전 플래그를 **임시로** 추가한다
   echo 'VERYUP_KEY_ROTATION=1' | sudo tee -a /etc/veryup/internal.env
   sudo systemctl restart veryup-internal
   sudo journalctl -u veryup-internal -n 60 --no-pager | grep -E '카나리아|회전 모드|복호화 불가'
   ```

   기동 로그에 다음이 나오면 정상이다(이 상태가 **의도된 회전 중** 상태다):

   ```
   마스터 키 카나리아  : ❌ 실패 — VERYUP_KEY_ROTATION=1 이라 기동만 허용했습니다. …
   복호화 불가 인증키    : 2건 — /keys 에서 삭제 후 재입력하세요
       ↳ #1 coupang / 메인계정 (InvalidToken)
   ```

   1. `/keys` 로 들어간다(관리 화면 상단에 보라색 회전 배너가 떠 있다).
   2. 복호화 불가 행을 연다 → **'복호화 실패' 안내가 뜨고 수정 폼이 없다**(빈 값으로 덮어써
      마지막 사본을 잃지 않게 한 것이다). 목록으로 돌아가 그 행을 **삭제**한다.
   3. 1번에서 재발급한 새 자격증명을 **새로 등록**한다.
   4. 전부 끝나면 **`VERYUP_KEY_ROTATION` 을 지우고 재기동**해 카나리아가 `통과` 로 바뀌는지 본다.
      ```bash
      sudo sed -i '/^VERYUP_KEY_ROTATION=/d' /etc/veryup/internal.env
      sudo systemctl restart veryup-internal
      sudo journalctl -u veryup-internal -n 40 --no-pager | grep 카나리아   # → 통과 — … 전부 복호화됨
      ```
      **이 마지막 단계를 빠뜨리면** 다음에 `KEY_MASTER` 를 잘못 넣어도 서버가 조용히 뜨고,
      `/api/credentials` 가 `data:null` 을 돌려주는 상태로 운영에 남는다.

   > 회전을 절반만 하고 재기동해도 막히지 않는다. 카나리아는 **한 건이라도 복호화되면 통과**로 보고
   > 못 읽은 행만 경고로 나열한다(예전에는 첫 행 하나만 봤고, 그 행이 정렬상 옛 행이라
   > 재입력을 다 끝낼 때까지 영원히 뜨지 않는 교착이 있었다).

   **4-B. 키를 바꾸지 않는 경우 — 새 환경변수로 그냥 띄운다.**
   카나리아가 바로 `통과` 여야 한다. 실패한다면 넣은 `KEY_MASTER` 가 이 `admin.db` 의 키가 아니다 —
   **회전 플래그로 넘기지 말고** 옛 `secret.key` 내용을 다시 확인하라.
   그런 다음 `/keys` 에서 필요한 자격증명을 점검한다.
5. **서버에서 `server/secret.key` 를 삭제한다.** 값은 이제 `EnvironmentFile`(0600) 에만 있다.
   작업 폴더(개인 PC 사본)의 `secret.key`·`admin.db` 도 삭제하고 `server/` 를 동기화 대상에서 뺀다.
   (회전한 경우에는 옛 키를 버리는 것이므로, **4-A 를 끝낸 뒤에** 지운다.)

### 3-3. 기존 관리자 계정 비밀번호 일괄 교체

기동 로그에 다음이 보이면 **아직 조치하지 않은 것**이다:

```
⚠ 비밀번호를 **확인했다고 표시되지 않은** 활성 관리자 계정 1개: admin
```

> **이 신호가 정확히 뜻하는 것**: 코드는 비밀번호를 볼 수 없다(해시만 저장한다). 볼 수 있는 것은
> `must_change_password` 플래그뿐이고, 기존 계정은 그 플래그가 0 이다. 그래서 이 경고는
> "이 계정은 **지금 알고 있는 비밀번호로 그대로 로그인된다**"까지만 말해 준다.
> **비밀번호를 바꿔도 플래그는 다시 0 이 되므로 경고는 저절로 사라지지 않는다** —
> 사람이 확인했다고 적어 주는 것(`VERYUP_ADMIN_PW_ACK`)이 유일한 종료 조건이다.

**조치(둘 다 한다).**

1. **비밀번호를 실제로 바꾼다.** 누가 무엇을 쓰는지 안다면 각자 `/password` 에서 바꾸면 되고,
   모르겠으면 아래 일괄 강제를 쓴다.
2. **확인했다고 적는다.** 내부 유닛에 `VERYUP_ADMIN_PW_ACK=아이디1,아이디2` 를 넣고 재기동하면
   경고와 배너가 꺼진다. 목록에 없는 관리자 계정이 새로 생기면 다시 뜬다(그게 이 장치의 목적이다).

**일괄 강제** — 내부 유닛에 `VERYUP_FORCE_ADMIN_PW_CHANGE=1` 을 **한 번만** 넣고 재기동한다.

   ```bash
   sudo systemctl set-environment VERYUP_FORCE_ADMIN_PW_CHANGE=1   # 또는 internal.env 에 임시 추가
   sudo systemctl restart veryup-internal
   sudo journalctl -u veryup-internal -n 20 --no-pager | grep FORCE
   # → "관리자 계정 N개에 비밀번호 강제 변경을 걸었습니다: ..."
   ```

   그 뒤 **환경변수를 반드시 지우고** 다시 재기동한다(남겨 두면 재기동마다 전원이 다시 걸린다).
   플래그가 걸린 계정은 다음 로그인에서 `/password` 로 리다이렉트되고, 바꾸기 전에는
   앱 `/api/login` 이 403 이다 — 즉 **직원 앱도 함께 멈춘다.** 업무 시간을 피해서 하라.

`VERYUP_ADMIN_PW_ACK` 에 아이디를 하나씩 적게 해 둔 이유는, '전부 무시' 스위치를 만들면
나중에 생긴 계정까지 같이 묻히기 때문이다. 목록에 없는 계정이 생기면 경고는 다시 뜬다.

> **더 확실한 방법:** 예전 관리자 계정을 쓰지 않을 거라면 `/staff` 에서 **비활성화**한다.
> 비활성 계정은 로그인도 안 되고(세션이 남아 있어도 즉시 끊긴다) 이 경고에서도 빠진다.

### 3-4. 이번 변경으로 **깨지는** 것 (전부 의도된 하위 호환 파괴)

| 증상 | 이유 | 대응 |
|---|---|---|
| **빈 DB** 에서 `admin/admin1234` 가 더 이상 안 만들어짐 | 기본계정 자동 생성 제거(감사 §1·2·4·7) | `BOOTSTRAP_ADMIN_USER/PW` 로 최초 계정 생성. ⚠ **기존 `admin.db` 의 그 계정은 여전히 로그인된다 — 3-3 을 반드시 처리하라** |
| 환경변수 없이 서버가 안 뜸 | `public.py`·`ebay_notify.py`·`config.py` 가 import 시점에 기동 거부 | 1절 표대로 주입 |
| 직원 앱이 인증키를 못 받음 | `/api/credentials` 가 `platform` 필수 + role 검사 | `STAFF_PLATFORMS` 설정. 앱은 플랫폼별로 호출해야 한다 |
| 직원이 앱 로그인 403 | 관리자가 만든/초기화한 계정은 `must_change_password=1` | 웹 `/password` 에서 비밀번호를 먼저 바꾸게 안내 |
| 비밀번호가 짧다고 거부 | 최소 6자 → **12자** | 12자 이상으로 |
| 자동 업데이트 401/404 | `UPDATE_TOKEN` 미설정 시 라우트 미등록, 설정 시 헤더 필수 | 서버와 Electron 양쪽에 같은 값 |
| `tests/` 가 깨짐 | 새 기동 검사·API 변경 반영 안 됨 | 후속 작업(6절) |

## 4. systemd 유닛

### 4-1. 공개 프로세스 `/etc/systemd/system/veryup-public.service`

```ini
[Unit]
Description=VERY UP 공개 서비스 (privacy / eBay 삭제 알림 수신)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=veryup-public
Group=veryup-queue
UMask=0007
WorkingDirectory=/opt/veryup/server
EnvironmentFile=/etc/veryup/public.env
ExecStart=/opt/veryup/server/.venv/bin/uvicorn serve_public:app \
    --host 127.0.0.1 --port 8080 \
    --workers 1 \
    --proxy-headers --forwarded-allow-ips 127.0.0.1
Restart=always
RestartSec=3

# ── 샌드박싱: 공개 표면이 만질 수 있는 것을 최소화한다
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/veryup
ProtectKernelTunables=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
MemoryMax=512M

[Install]
WantedBy=multi-user.target
```

> **`--workers 1` 인 이유:** eBay 레이트리밋이 프로세스 메모리 기준이다. 워커를 여러 개 띄우면
> 실효 한도가 워커 수만큼 곱해진다. 더 막고 싶으면 nginx `limit_req` 를 한 겹 더 둔다.
>
> **`--host 127.0.0.1` 인 이유:** TLS 는 nginx 가 끝낸다. `0.0.0.0` 으로 직접 열면 평문 http 가
> 인터넷에 그대로 노출된다.
>
> **`public.env` 에 반드시 들어가야 하는 것:** `EBAY_QUEUE_DIR=/var/lib/veryup`,
> `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET`.
>
> 세 변수의 **기동 거부 조건은 서로 다르다**(예전 이 자리의 "셋 중 하나라도 없으면 뜨지 않는다"는 부정확했다):
> - `EBAY_CLIENT_ID` / `EBAY_CLIENT_SECRET` — 없으면 기본 STRICT 모드에서 **무조건** 기동 거부.
> - `EBAY_QUEUE_DIR` — **조건부다.** 미설정이면 소스 디렉터리를 큐 위치로 쓰면서 경고만 남기고,
>   **그 디렉터리에 `admin.db` 가 있을 때에만** 기동을 거부한다(`serve_public.py:196-204`).
>   운영 서버에서는 `admin.db` 가 같은 디렉터리에 있으므로 결과적으로 거부되지만, `admin.db` 를
>   다른 곳에 둔 서버에서는 **조용히 소스 디렉터리에 큐가 생긴다** — 배포마다 큐가 갈리고
>   `/deletions` 는 빈 화면이 된다. 그러니 값은 항상 명시하라.
>
> **`EBAY_QUEUE_DIR` 은 영속 경로여야 한다.** `/tmp`·`/var/tmp`·`/run` 같은 휘발성 경로,
> 그리고 `PrivateTmp=yes` 아래의 `/tmp` 는 쓰지 마라. 런타임에 그 디렉터리가 사라지면
> `ebay_queue` 는 **스스로 복구하지 않는다** — 알림 적재와 거절 감사기록이 조용히 비고,
> 밖에서 보이는 응답 코드는 정상이라 아무도 알아채지 못한다.
> - `ReadWritePaths=/var/lib/veryup` 가 곧 `EBAY_QUEUE_DIR` 이어야 한다. 값을 옮기면 이 줄도 같이 옮겨라
>   (안 옮기면 `ProtectSystem=strict` 때문에 큐 쓰기가 실패하고, 검증을 통과한 알림이 503 으로 되튕긴다).
> - `systemd-tmpfiles` 자동 청소에서 **제외**하라. `/etc/tmpfiles.d/` 에 `/var/lib/veryup` 를 age 옵션과 함께
>   적는 설정을 두지 말고, 이미 있다면 지운다. 확인:
>   ```bash
>   systemd-tmpfiles --cat-config | grep -n 'veryup\|/var/lib'   # 청소 규칙에 걸려 있지 않은가
>   systemd-analyze unit-paths >/dev/null; ls -ld /var/lib/veryup
>   ```
> - `RuntimeDirectory=` / `PrivateTmp=` 로 만들어지는 경로를 큐 디렉터리로 **재활용하지 마라**
>   (유닛이 멈출 때 통째로 사라진다).

### 4-2. 내부 프로세스 `/etc/systemd/system/veryup-internal.service`

```ini
[Unit]
Description=VERY UP 관리 서버 (내부 전용, WireGuard 바인드)
After=network-online.target wg-quick@wg0.service
Requires=wg-quick@wg0.service          # WireGuard 가 떠야 10.8.0.1 에 바인드할 수 있다
Wants=network-online.target

[Service]
Type=simple
User=veryup
Group=veryup-queue
UMask=0007
WorkingDirectory=/opt/veryup/server
EnvironmentFile=/etc/veryup/internal.env
# ⚠ --host 는 WireGuard 인터페이스 주소여야 한다. 0.0.0.0 을 쓰면 분리가 무효가 된다.
# ⚠ --proxy-headers 를 쓰지 않는다. 앞에 리버스 프록시가 없는 구성이므로 X-Forwarded-For 는
#    전부 클라이언트(피어)가 지어낸 값이다. 믿는 순간 로그인 IP 잠금이 우회되고 감사 로그가 위조된다.
#    (예전 예시의 `--forwarded-allow-ips 10.8.0.1` 은 이 서버 자신의 주소라 어느 구성에도 맞지 않았다.)
ExecStart=/opt/veryup/server/.venv/bin/uvicorn serve_internal:app \
    --host 10.8.0.1 --port 8001
Restart=always
RestartSec=3

NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/opt/veryup/server /var/lib/veryup /var/log/veryup
ProtectKernelTunables=yes
ProtectControlGroups=yes

[Install]
WantedBy=multi-user.target
```

> **구성 (B) — 같은 호스트의 nginx 가 내부 프로세스 앞에 붙는다면**(내부 TLS 종단이나 6-4 의 임시
> Basic auth) `ExecStart` 를 이렇게 바꾸고 `internal.env` 에 `FORWARDED_ALLOW_IPS=127.0.0.1` 을 넣는다:
>
> ```ini
> ExecStart=/opt/veryup/server/.venv/bin/uvicorn serve_internal:app \
>     --host 127.0.0.1 --port 8001 \
>     --proxy-headers --forwarded-allow-ips 127.0.0.1
> ```
>
> 신뢰 대상은 **nginx 가 붙어 오는 주소**지 이 서버의 WireGuard 주소가 아니다. 그리고 이 구성에서는
> nginx 가 `X-Forwarded-For` 를 **반드시** 넣어야 한다(5절 `proxy_params`). 넣지 않으면 모든 요청이
> `127.0.0.1` 로 찍히는데, `app.py` 는 루프백 IP 를 잠금 판정에서 제외하므로
> **IP 별 로그인 잠금이 사실상 꺼진다**(계정별 5회 잠금만 남는다).
>
> 두 구성 모두 `FORWARDED_ALLOW_IPS=*` / `0.0.0.0/0` 은 **기동 거부**다.
> systemd 의 `ExecStart` 에 적은 `--forwarded-allow-ips '*'` 도 진입점이 argv 에서 잡아낸다.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now veryup-public
sudo journalctl -u veryup-public -n 50 --no-pager     # 노출 경로 목록이 찍힌다
```

기동 로그에 **인터넷에 열린 경로 목록**이 그대로 출력된다. 그 목록 밖의 경로가 인터넷에서
응답한다면 그것은 코드 문제가 아니라 nginx 설정 문제다.

## 5. 리버스 프록시

> ### ⚠ 현재 운영 서버는 nginx 가 아니라 **Caddy** 로 돌고 있다 (2026-09-17 실측)
>
> 이 절은 nginx 를 전제로 쓰였지만, `admin.veryup-domain.duckdns.org` 의 실제 응답 헤더는
> `Via: 1.1 Caddy` · `Server: Caddy` 이고 그 뒤에 `Server: uvicorn` 이 있다.
> TLS 인증서는 Let's Encrypt, HTTP(80) 는 308 로 HTTPS 리디렉션된다 — Caddy 의 기본 동작이다.
>
> **그리고 지금 Caddy 는 경로를 가리지 않고 전부 앱으로 넘긴다.** `/login`·`/keys`·`/staff`·
> `/api/credentials` 가 모두 uvicorn 까지 도달하고, 없는 경로(`/nonexistent-xyz`)까지 앱이 404 를 낸다.
> 즉 **화이트리스트가 없다.** 아래 nginx 설정이 하려는 "공개 도메인은 공개 프로세스로만" 은
> 이 서버에 아직 적용돼 있지 않다.
>
> 실무상 의미가 둘이다.
> 1. **`/updates` 를 열려고 프록시를 건드릴 필요가 없다.** 앱에 라우트가 생기는 순간 바로 공개 주소로 닿는다
>    (= `UPDATE_TOKEN` 을 설정하고 `public.py` 가 올라가 있으면 끝).
> 2. 반대로 **`/keys`·`/api/*` 도 지금 그대로 인터넷에 열려 있다.** 표면 분리를 실제로 적용하려면
>    아래 nginx 설정을 Caddy 로 옮겨 써야 한다. Caddyfile 로는 이렇게 된다:
>
> ```caddyfile
> # 공개 도메인 — 공개 프로세스로만
> public.veryup-domain.duckdns.org {
>     handle /privacy*    { reverse_proxy 127.0.0.1:8080 }
>     handle /ebay/auth/* { reverse_proxy 127.0.0.1:8080 }
>     handle /ebay/deletion { reverse_proxy 127.0.0.1:8080 }
>     handle { respond 404 }          # 화이트리스트 밖은 전부 차단
> }
>
> # 관리 도메인 — 자동 업데이트 파일만 (5-1 참고)
> admin.veryup-domain.duckdns.org {
>     handle /updates* {
>         reverse_proxy 127.0.0.1:8001
>     }
>     handle { respond 404 }          # /login·/keys·/api/* 를 인터넷에서 걷어낸다
> }
> ```
>
> > **⛔ 바인드 주소를 먼저 맞춰라 — 안 맞추면 502 다.**
> > 위 `reverse_proxy 127.0.0.1:8001` 은 내부 프로세스가 **루프백에 떠 있을 때만** 닿는다.
> > 그런데 4-2 의 기본 `ExecStart` 는 `--host 10.8.0.1`(WireGuard 주소)로 뜬다 —
> > 그 상태에서는 127.0.0.1:8001 에 **아무도 듣고 있지 않아** 프록시가 502 를 뱉는다.
> > 프록시를 앞에 두기로 했다면 둘 중 하나를 골라라(섞지 마라):
> >   1. `ExecStart` 를 4-2 의 **구성 (B)** 로 바꾼다 — `--host 127.0.0.1` + `internal.env` 에 `FORWARDED_ALLOW_IPS=127.0.0.1`
> >   2. 바인드는 그대로 두고 프록시 대상을 `10.8.0.1:8001` 로 적는다
> > 확인: `sudo ss -tlnp | grep 8001` 의 Local Address 가 프록시가 적은 주소와 같아야 한다.
>
> `handle` 은 **첫 일치 하나만** 실행된다(nginx 의 `location` 과 같은 감각).
> `handle_path` 와 헷갈리지 마라 — 그쪽은 매칭된 접두사를 **떼고** 넘긴다.
> 적용은 `caddy validate --config /etc/caddy/Caddyfile` 로 검사한 뒤
> `sudo systemctl reload caddy` 다. reload 는 무중단이다.


핵심: **공개 도메인은 공개 프로세스로만 프록시한다.** 내부 프로세스 포트로 가는
`proxy_pass` 를 단 한 줄도 쓰지 않는다.

`/etc/nginx/sites-available/veryup-public`:

```nginx
# eBay 알림 폭주를 앱 앞에서 한 겹 더 자른다 (앱 레이트리밋은 프로세스 메모리 기준이라 보완이 낫다)
limit_req_zone $binary_remote_addr zone=ebay:10m rate=30r/m;

server {
    listen 80;
    listen [::]:80;
    server_name public.veryup-domain.duckdns.org;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name public.veryup-domain.duckdns.org;

    ssl_certificate     /etc/letsencrypt/live/public.veryup-domain.duckdns.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/public.veryup-domain.duckdns.org/privkey.pem;

    # 이 서버 블록에서 위로 갈 수 있는 곳은 공개 프로세스 하나뿐이다.
    set $veryup_public http://127.0.0.1:8080;

    add_header X-Content-Type-Options nosniff always;
    add_header X-Frame-Options DENY always;
    add_header Referrer-Policy no-referrer always;

    client_max_body_size 128k;          # 삭제 알림은 1KB 안팎이다

    location = /ebay/deletion {
        limit_req zone=ebay burst=10 nodelay;
        proxy_pass $veryup_public;
        include /etc/nginx/proxy_params;
    }

    location /privacy     { proxy_pass $veryup_public; include /etc/nginx/proxy_params; }
    location /ebay/auth/  { proxy_pass $veryup_public; include /etc/nginx/proxy_params; }

    # 화이트리스트 밖은 전부 차단. /login, /keys, /api/*, /updates 가 여기에 걸린다.
    location / { return 404; }
}
```

`/etc/nginx/proxy_params` 에 다음이 들어 있어야 한다(없으면 만든다):

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

### 5-1. `admin.` 호스트의 `/updates` 예외 (자동 업데이트를 쓸 때만)

위 `veryup-public` 블록은 **공개 도메인**의 것이고 거기서는 `/updates` 를 그대로 404 로 둔다.
문제는 직원 PC 의 자동 업데이트다. `package.json` 의 `build.publish.url` 이
`https://admin.veryup-domain.duckdns.org/updates/` 인데, 분리 후 `/updates` 는 내부 프로세스로
가고 내부는 WireGuard 뒤에 있다. **직원 노트북은 VPN 밖이므로 영영 닿지 못한다.**

자동 업데이트를 포기하지 않으려면 `admin.` 호스트에 **딱 이 한 경로만** 예외로 연다.

```nginx
server {
    listen 443 ssl http2;
    server_name admin.veryup-domain.duckdns.org;

    ssl_certificate     /etc/letsencrypt/live/admin.veryup-domain.duckdns.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.veryup-domain.duckdns.org/privkey.pem;

    # 설치본은 93MB 다. 기본 proxy 버퍼로는 디스크 임시파일을 타며 느려진다.
    proxy_buffering off;
    proxy_read_timeout 300s;

    # 업데이트 파일만. 하위 경로가 없는 정확 매칭 두 개 + 파일 하나.
    location /updates {
        proxy_pass http://127.0.0.1:8001;
        include /etc/nginx/proxy_params;
    }

    # 그 외 내부 경로(/login, /keys, /api/*, 프록시 릴레이)는 인터넷에 열지 않는다.
    location / { return 404; }
}
```

> **⛔ `proxy_pass` 주소가 실제 바인드 주소와 같아야 한다.** 4-2 의 기본 `ExecStart` 는
> `--host 10.8.0.1` 이라 위의 `127.0.0.1:8001` 로는 **502** 가 난다. 구성 (B)(`--host 127.0.0.1`)
> 로 바꾸거나, `proxy_pass http://10.8.0.1:8001;` 로 적어라. `sudo ss -tlnp | grep 8001` 로 확인.

**이 예외가 무엇을 바꾸고 무엇을 바꾸지 않는가**

- 바뀌는 것: 인터넷에서 `admin.` 의 `/updates` 로 TCP 가 내부 프로세스까지 닿는다.
- 바뀌지 않는 것: `UPDATE_TOKEN` 이 없으면 `public.py` 가 **라우트 자체를 등록하지 않는다**(404).
  있으면 `X-Update-Token` 이 맞아야 한다. 즉 토큰 없는 요청은 파일 목록도 못 본다.
- `admin.db`·`KEY_MASTER` 는 그대로 내부에만 있다. 이 경로가 내주는 것은 설치본 파일뿐이다.

**반드시 같이 해야 하는 것.** 서버 `UPDATE_TOKEN` 과 직원 PC 의
`%APPDATA%ery-up-ver2eryup.env` 의 `UPDATE_TOKEN` 이 **같은 값**이어야 한다.
한쪽만 설정하면 전원이 조용히 업데이트를 못 받는다(앱 화면에는 거의 드러나지 않는다).
견본은 저장소 루트 `veryup.env.example`.

**확인 방법**

```bash
# 토큰 없이 → 404 (라우트 자체가 안 보인다)
curl -s -o /dev/null -w '%{http_code}
' https://admin.veryup-domain.duckdns.org/updates

# 토큰 주고 → {"ready":true,...}
curl -s -H "X-Update-Token: $UPDATE_TOKEN" https://admin.veryup-domain.duckdns.org/updates
```

> 자동 업데이트를 **쓰지 않기로** 했다면 이 절을 통째로 건너뛰고,
> 대신 `src/main_process.js` 의 `setupAutoUpdate()` 호출을 지워라. 지우지 않으면
> 앱이 켜질 때마다 닿지 않는 주소로 요청을 보내고 조용히 실패한다.

> ## ⛔ `EBAY_TRUST_FORWARDED=1` 은 넣지 마라 (예전 가이드의 지시를 철회한다)
>
> 예전에 이 자리에는 "`X-Forwarded-For` 를 실제로 쓰려면 `EBAY_TRUST_FORWARDED=1` 을 넣어라,
> 넣지 않으면 모든 요청이 nginx IP 로 보여 IP 별 레이트리밋이 전역 카운터처럼 동작한다"고 적혀 있었다.
> **두 문장 모두 틀렸다.**
>
> 1. **이미 실제 IP 로 보인다.** 공개 유닛은 `--proxy-headers --forwarded-allow-ips 127.0.0.1` 로 뜨므로
>    uvicorn 의 `ProxyHeadersMiddleware` 가 `scope["client"]` 를 실제 클라이언트 주소로 바꿔 놓는다.
>    그 미들웨어는 헤더를 **오른쪽에서부터** 훑어 신뢰 프록시(127.0.0.1)를 걷어낸 **마지막 비신뢰 주소**를 쓴다.
> 2. **켜면 오히려 스푸핑이 열린다.** `ebay_notify._client_ip()` 는 헤더의 **맨 왼쪽** 값을 집는데,
>    nginx 의 `$proxy_add_x_forwarded_for` 는 **클라이언트가 보낸 값 뒤에** 실 IP 를 덧붙인다.
>    즉 맨 왼쪽은 언제나 **요청자가 직접 써 넣은 문자열**이다.
>
> 실측(헤더 `X-Forwarded-For: 1.2.3.4, 203.0.113.9`):
>
> | | 값 | 판정 |
> |---|---|---|
> | uvicorn `request.client.host` | `203.0.113.9` | 정확(실제 클라이언트) |
> | `_client_ip()` (`EBAY_TRUST_FORWARDED=1`) | `1.2.3.4` | **공격자가 지정한 값** |
>
> 켜 두면 공격자가 요청마다 다른 `X-Forwarded-For` 를 붙이는 것만으로 IP 별 레이트리밋(기본 120/분)과
> 공개키 조회 상한(기본 3/분)을 무한히 우회한다 — 무인증 POST 1건이 eBay API 호출 1건으로 증폭되는
> 그 경로다. 거절 감사기록의 `source_ip` 도 같이 오염된다.
>
> **결론: `EBAY_TRUST_FORWARDED` 는 `public.env` 에 아예 적지 마라.** 미설정이 정답이고,
> 그 상태에서 레이트리밋 키는 uvicorn 이 이미 복원해 둔 실제 클라이언트 주소다.
> (`proxy_params` 의 `X-Forwarded-For` 줄 자체는 그대로 둔다 — uvicorn 이 그 헤더를 쓴다.)

## 6. WireGuard 최소 설정

사무실 공인 IP 가 유동이므로 인바운드 IP 허용목록은 쓸 수 없다. VPN 으로 간다.

### 6-1. EC2 (서버)

```bash
sudo apt install -y wireguard
wg genkey | sudo tee /etc/wireguard/server.key | wg pubkey | sudo tee /etc/wireguard/server.pub
sudo chmod 600 /etc/wireguard/server.key
```

`/etc/wireguard/wg0.conf` (권한 0600):

```ini
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <서버 개인키>
# 사무실 트래픽을 인터넷으로 내보내지 않는다 — 이 VPN 의 용도는 관리 서버 접근뿐이다.
# (NAT 를 걸면 직원 인터넷이 전부 EC2 를 타고 나가 요금과 지연이 늘어난다)

[Peer]
# 사무실 PC 1
PublicKey = <사무실 PC 공개키>
AllowedIPs = 10.8.0.11/32
```

```bash
sudo sysctl -w net.ipv4.ip_forward=0        # 라우터가 아니다. 포워딩은 끈다
sudo systemctl enable --now wg-quick@wg0
sudo wg show
```

### 6-2. 사무실 PC (피어)

WireGuard 공식 클라이언트에 터널을 추가한다.

```ini
[Interface]
PrivateKey = <사무실 PC 개인키>
Address = 10.8.0.11/32

[Peer]
PublicKey = <서버 공개키>
Endpoint = <EC2 탄력 IP>:51820
# 관리 서버 대역만 터널로 보낸다(스플릿 터널). 0.0.0.0/0 을 쓰면 모든 인터넷이 EC2 를 탄다.
AllowedIPs = 10.8.0.0/24
PersistentKeepalive = 25
```

접속 확인: `http://10.8.0.1:8001/login`
직원 앱의 `ADMIN_SERVER_URL` 도 `http://10.8.0.1:8001` 로 바꾼다.

> **평문 http 로 쓸 경우** 내부 유닛에 `SESSION_HTTPS_ONLY=0` 을 넣어야 로그인이 된다.
> 이 구성에서는 WireGuard 가 암호화를 담당한다. 내부에도 TLS 를 붙일 수 있으면 그 편이 낫다.

### 6-3. 피어 추가/제거

```bash
sudo wg set wg0 peer <새 공개키> allowed-ips 10.8.0.12/32   # 추가(즉시 반영)
sudo wg set wg0 peer <떠난 공개키> remove                    # 제거
sudo wg-quick save wg0                                       # wg0.conf 에 영구 반영
```

퇴사자 처리는 **세 곳 모두** 해야 한다: WireGuard 피어 제거 + `/staff` 비활성화 + 비밀번호 변경.

### 6-4. 임시 대안 — nginx Basic auth

WireGuard 구축까지 시간이 걸린다면, 그 사이의 **임시** 조치로 쓴다.
VPN 을 대체하지는 못한다(관리 UI 가 여전히 인터넷에 있고, Basic 자격증명 하나가 유일한 벽이다).

```bash
sudo apt install -y apache2-utils
sudo htpasswd -c /etc/nginx/veryup.htpasswd office     # 20자 이상 난수
sudo chmod 640 /etc/nginx/veryup.htpasswd
sudo chown root:www-data /etc/nginx/veryup.htpasswd
```

```nginx
server {
    listen 443 ssl http2;
    server_name admin.veryup-domain.duckdns.org;
    # ssl_certificate ... (생략)

    auth_basic "VERY UP 관리";
    auth_basic_user_file /etc/nginx/veryup.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:8001;
        include /etc/nginx/proxy_params;
    }
}
```

임시 구성에서는 내부 프로세스를 `--host 127.0.0.1` 로 띄운다(외부 인터페이스 금지).
이때가 4-2 의 **구성 (B)** 다 — `--proxy-headers --forwarded-allow-ips 127.0.0.1` 을 붙이고
`internal.env` 에 `FORWARDED_ALLOW_IPS=127.0.0.1` 을 넣어야 로그인 잠금과 감사 로그에 진짜 IP 가 남는다
(`*` 를 넣으면 기동을 거부한다).
**주의:** 앱(`/api/*`)과 프록시 릴레이는 Basic auth 헤더를 보내지 못하므로 그대로는 동작하지 않는다.
앱 경로만 예외로 빼면 `/api/login` 이 다시 인터넷에 열리므로, 이 구성은 **사람이 쓰는 웹 UI 를
급히 가리는 용도**로만 쓰고 빨리 WireGuard 로 넘어가라.

## 7. 배포 순서

**공개 먼저, 내부 나중.** eBay 심사는 공개 표면만 필요로 하므로 내부 수정이 끝나기를 기다릴 이유가 없다.

### 7-1. 1단계 — 공개 프로세스

1. `/etc/veryup/public.env` 작성(1-1 표), 권한 0600.
2. `sudo systemctl enable --now veryup-public`
3. `journalctl -u veryup-public` 에서 확인:
   - 노출 경로 목록이 **6줄**(privacy, privacy/en, ebay auth 2, deletion GET/POST)인가
   - `KEY_MASTER`/`ADMIN_SECRET` 경고가 **없는가**
   - `GET 검증 토큰: 설정됨`, `서명 검증 자격증명: 설정됨` 인가
   - `EBAY_QUEUE_DIR` 이 `admin.db` 가 있는 디렉터리와 **다른가**(같으면 애초에 뜨지 않는다)
4. nginx 반영: `sudo nginx -t && sudo systemctl reload nginx`
5. 외부에서 확인:
   ```bash
   curl -s https://public.<도메인>/privacy | head -20      # 200, [[ 가 없어야 한다
   curl -s https://public.<도메인>/privacy/en | head -5     # 200
   curl -s -o /dev/null -w '%{http_code}\n' https://public.<도메인>/login    # 404 여야 한다
   curl -s -o /dev/null -w '%{http_code}\n' https://public.<도메인>/keys     # 404 여야 한다
   curl -s 'https://public.<도메인>/ebay/deletion?challenge_code=test123'    # challengeResponse
   ```
6. eBay 개발자 포털에 등록: 알림 엔드포인트 = `EBAY_DELETION_ENDPOINT`,
   개인정보처리방침 URL = **`/privacy/en`**(심사관은 영어권이다).
   포털의 "Send Test Notification" 으로 검증 통과를 확인한다.
7. `sqlite3 /var/lib/veryup/ebay_queue.db 'select reason,count(*) from rejections group by 1;'`
   → `public-key:...` 나 `signature-mismatch` 가 쌓이면 eBay 응답 형식이 구현 가정과 다른 것이다.
   **진짜 알림을 버리고 있다는 뜻일 수 있으니 즉시 확인하라.**

### 7-2. 2단계 — 내부 프로세스

1. WireGuard 를 먼저 올리고 사무실 PC 에서 `10.8.0.1` 핑이 되는지 확인.
2. `/etc/veryup/internal.env` 작성(1-2 표), 권한 0600. 3절의 키 회전 순서를 지킬 것.
3. `sudo systemctl enable --now veryup-internal`
4. `journalctl -u veryup-internal` 확인:
   - `mode=production` 인가 (아니면 애초에 뜨지 않는다 — `VERYUP_ENV` 미설정은 기동 거부다)
   - `마스터 키 카나리아` 줄이 `통과 — 저장된 인증키 N건 전부 복호화됨` 인가.
     실패하면 기동이 멈춘다 = `KEY_MASTER` 가 이 `admin.db` 를 암호화한 키가 아니라는 뜻이다.
     **의도한 회전이 아니라면 그 상태로 우회해 띄우지 마라** — `/api/credentials` 가
     조용히 `data:null` 을 돌려주고 직원 앱이 이유 없이 실패한다.
     의도한 회전이라면 3-2 의 4-A(`VERYUP_KEY_ROTATION=1`)를 따르고, **끝나면 그 변수를 지운다**
   - `복호화 불가 인증키` 줄이 있으면 그 행들은 옛 키로 암호화된 값이다 → `/keys` 에서 삭제·재입력
   - `🔑 KEY_MASTER 회전 모드` 경고 블록이 보이는가 → 회전 작업이 끝났는데도 보이면
     `VERYUP_KEY_ROTATION` 을 **지우지 않은 것**이다(9절 체크리스트)
   - `eBay 큐 디렉터리` 가 공개 유닛의 `EBAY_QUEUE_DIR` 과 같은가
   - `신뢰 프록시(FORWARDED_ALLOW_IPS)` 가 구성 (A)면 미설정, (B)면 `127.0.0.1` 인가
   - `비밀번호 미확인 관리자` 가 **없음** 인가 → ⚠ 가 붙어 있으면 3-3 을 지금 처리하라
   - `/updates` 상태
5. 사무실 PC 에서 `http://10.8.0.1:8001/login` → 부트스트랩 계정으로 로그인 → 즉시 비밀번호 변경.
   기존 `admin.db` 를 들고 온 경우라면 **넘어온 관리자 계정 전부**의 비밀번호를 바꾼다(3-3).
6. **인터넷에서 닫혔는지 반드시 확인한다**(다른 네트워크에서):
   ```bash
   curl -m 5 -o /dev/null -w '%{http_code}\n' http://<EC2 공인 IP>:8001/login   # 연결 실패여야 한다
   curl -m 5 -o /dev/null -w '%{http_code}\n' https://public.<도메인>/login      # 404 여야 한다
   ```
7. `/proxy/health` 로 아웃바운드 IP 를 확인하고, 그 값이 마켓플레이스 허용목록의 IP 와 같은지 본다.
8. `/deletions` 에서 eBay 큐가 보이는지 확인.

## 8. eBay 삭제 요청 처리 (`/deletions`)

공개 프로세스의 `POST /ebay/deletion` 은 **더 이상 인증키를 지우지 않는다**(감사 §19·§26).
서명 검증을 통과한 알림을 `pending` 으로 쌓을 뿐이고, 실제 삭제는 관리자가 여기서 승인할 때만 일어난다.

- 접근: 내부 프로세스 `http://10.8.0.1:8001/deletions` (admin 역할 전용)
- **승인·삭제** — 해당 eBay userId 와 일치하는 **eBay 플랫폼 인증키만** 삭제하고
  `key_access_logs` 에 `delete` 로 남긴다(`/logs` 에서 보인다). 다른 플랫폼은 건드리지 않는다.
- **기각** — 지우지 않고 항목만 닫는다. 기각도 감사 로그에 남는다.
- `matched=0` 은 **정상**이다. 이 앱의 인증키는 '플랫폼+별칭' 기준으로 저장되지 구매자 계정에
  매여 있지 않다. "지울 것이 없었다"는 것이 곧 이행 증빙이다.
- **이행 기한은 수신일로부터 30일이다.** 대기 건수를 주 1회는 확인하라.
  (코드가 기한을 강제하지 않는다 — 넘겨도 자동으로 지워지거나 경보가 뜨지 않는다.)
- 화면 하단의 "최근 거절 기록"이 갑자기 늘면 공개 프로세스가 진짜 알림을 버리고 있을 수 있다.
- **격리 본문 열람** — 거절 기록의 `격리` 열에 id 가 있으면 누른다. 공개 프로세스가 보관해 둔
  **알림 원본**이 열린다(`/deletions/quarantine/<id>`). 우리가 정당한 알림을 잘못 거절했을 때
  userId 를 되찾아 수동으로 이행할 수 있는 유일한 경로다 — eBay 는 2xx 를 받은 알림을 다시 보내지 않는다.
  보관 상한(기본 검증분 4MB / 미검증분 1MB)을 넘기면 오래된 것부터 회전으로 사라진다.
  ⚠ 미검증 본문은 **누구나 만들어 보낼 수 있다.** 거기 적힌 userId 로 삭제를 이행하기 전에
  거절 사유가 '우리 쪽 장애'(`token-unavailable`, `public-key-*`)인지 먼저 확인하라.
- 승인·기각 버튼은 CSRF 토큰을 함께 보낸다. 세션이 만료된 탭에서 누르면 403 안내 화면이 뜨는데,
  다시 로그인하고 목록을 새로 열면 된다(스크립트로 이 경로를 자동화하려면 `GET /deletions` 로
  토큰부터 받아야 한다).

배포 직후 한 번, 이후 분기마다:

- [ ] `journalctl -u veryup-internal | grep '비밀번호 미확인'` → **없음** 인가 (아니면 3-3)

- [ ] `journalctl -u veryup-public | grep -i 'KEY_MASTER\|ADMIN_SECRET'` → 아무것도 안 나오는가

- [ ] `ls /opt/veryup/server/secret.key` → **없는가**(KEY_MASTER 로 옮기고 지웠는가)

- [ ] `/etc/veryup/*.env` 권한이 0600 이고 백업·동기화 대상이 아닌가

## 10. 문제 해결

| 증상 | 원인 | 대응 |
|---|---|---|
| 공개 프로세스가 안 뜸: `개인정보처리방침 환경변수가 비어 있습니다` | `COMPANY_NAME`/`CONTACT_EMAIL`/`DATA_RETENTION` 미설정 | 1-1 표대로 주입 |
| 공개 프로세스가 안 뜸: `EBAY_DELETION_ENDPOINT 환경변수가 필요합니다` | 하드코딩 기본값 제거됨 | 포털에 등록한 URL 을 넣는다. 경로는 `/ebay/<이름>` |
| 공개 프로세스가 안 뜸: `PublicSurfaceError` | 공개 유닛에 `KEY_MASTER` 등이 들어 있음 | `EnvironmentFile` 을 분리한다 |
| 내부 프로세스가 안 뜸: `InternalStartupError ... ADMIN_SECRET` | 비밀값 미주입 | 1-2 표. 로컬 개발이면 `VERYUP_ALLOW_DEV_SECRETS=1` |
| 내부 프로세스가 안 뜸: `... VERYUP_ENV 가 설정되지 않았습니다` | 모드를 명시하지 않았다 | 운영 `VERYUP_ENV=production`, 개발 `VERYUP_ENV=development`. `prod` 같은 줄임말은 안 된다 |
| 내부 프로세스가 안 뜸: `... 와일드카드 * 가 있습니다` | `FORWARDED_ALLOW_IPS` 또는 `--forwarded-allow-ips` 가 `*`/`0.0.0.0/0` | 4-2 구성 (A)면 비우고, (B)면 `127.0.0.1` |
| 내부 프로세스가 안 뜸: `KEY_MASTER 로 저장된 인증키를 **한 건도** 복호화하지 못했다` | 기동 시 카나리아 검사 — 형식은 맞지만 **다른 키** | 의도치 않았다면 예전 `server/secret.key` 의 내용을 그대로 넣는다. **의도적 회전이면 `VERYUP_KEY_ROTATION=1` 로 띄우고**(3-2 의 4-A) `/keys` 에서 옛 행 삭제 → 재입력 → **그 변수 제거 후 재기동**. `VERYUP_ALLOW_DEV_SECRETS` 를 대신 쓰지 마라 |
| 기동은 되는데 `마스터 키 카나리아 : ⚠ 부분 실패` | 일부 행만 옛 `KEY_MASTER` 로 암호화돼 있다(회전 미완료 또는 암호문 손상) | 기동 로그의 `복호화 불가 인증키` 목록을 보고 `/keys` 에서 그 행을 삭제한 뒤 새 값으로 다시 등록한다. 한 건이라도 읽히면 기동은 막지 않는다(회전 교착 방지) |
| 관리 화면 상단에 **보라색** 배너(`KEY_MASTER 회전 모드`) | `VERYUP_KEY_ROTATION=1` 이 아직 들어 있다 | 재입력이 끝났으면 `internal.env` 에서 지우고 재기동. 남겨 두면 다음 `KEY_MASTER` 사고가 조용히 통과한다 |
| 내부 프로세스가 안 뜸: `SecretConfigError` | 두 값이 같거나 `ADMIN_SECRET` 이 32자 미만 | 서로 다른 난수로. ⚠ 이 검사는 이제 **개발 모드에도** 적용된다 |
| 공개 프로세스가 안 뜸: `EBAY_CLIENT_ID ...` / `admin.db ...` | 기본 STRICT 모드의 자가 점검 | 자격증명을 넣거나 `EBAY_QUEUE_DIR` 을 `admin.db` 와 다른 디렉터리로. 개발 트리에서만 `PUBLIC_STRICT=0` |
| 관리 화면 상단에 빨간 배너 | 비밀번호를 확인했다고 표시되지 않은 관리자 계정이 있다 | 3-3. 비밀번호를 바꾼 뒤 `VERYUP_ADMIN_PW_ACK` 에 아이디를 적어야 꺼진다(비밀번호 변경만으로는 안 꺼진다) |
| `/deletions` 승인·기각이 403 | CSRF 토큰 불일치(대개 만료된 탭) | 다시 로그인하고 목록을 새로 열어 누른다 |
| eBay 엔드포인트 검증 503 | `EBAY_VERIFICATION_TOKEN` 미설정 | 포털의 토큰을 넣고 재기동 |
| 알림이 큐에 안 쌓이고 `rejections` 만 늘어남 | `EBAY_CLIENT_ID/SECRET` 없음 또는 서명 검증 실패 | `reason` 을 본다. `no-ebay-credentials` 면 자격증명, `signature-mismatch` 면 eBay 응답 형식 확인 |
| `/deletions` 에 "큐 파일이 아직 없습니다" | 공개 프로세스 미기동, 또는 `EBAY_QUEUE_DIR` 불일치 | 두 유닛의 값을 같게 |
| `/deletions` 에서 큐를 읽지 못함 | 파일 권한 | 2절의 그룹·setgid·UMask 설정 |
| 로그인이 계속 실패(비밀번호는 맞음) | `SESSION_HTTPS_ONLY=1` + 평문 http | `SESSION_HTTPS_ONLY=0` (VPN 이 암호화 담당) |
| 로그인 429 | 계정 5회 / IP 20회 실패 잠금(15분) | 기다리거나 원인 확인. `/logs` 점검 |
| 직원 앱이 인증키를 못 받음 | `STAFF_PLATFORMS` 미설정, 또는 앱이 `platform` 없이 호출 | 환경변수 설정 + 앱이 플랫폼별로 호출하게 |
| 직원 앱 로그인 403 `must_change_password` | 관리자가 만든/초기화한 계정 | 웹 `/password` 에서 먼저 변경 |
| 자동 업데이트 404 | `UPDATE_TOKEN` 미설정 → 라우트 미등록 | 서버·클라이언트 양쪽에 같은 값 |
| 자동 업데이트 401 | 한쪽만 설정됨 | 값이 정확히 같은지 확인 |
| 프록시 릴레이가 마켓플레이스에서 거부됨 | 아웃바운드 IP 가 허용목록에 없음 | `/proxy/health` 의 IP 를 등록. 릴레이를 EC2 밖으로 옮기지 마라 |
| 잠금·권한거부 경고가 안 보임 | 루트 로거 핸들러 없음 | 두 진입점이 이제 설정한다. 파일로도 남기려면 `LOG_FILE` |

## 11. 아직 남은 일 (이 가이드 범위 밖)

- `tests/*.py` 를 새 동작 기준으로 다시 작성(기동 검사 환경변수, `platform` 필수,
  eBay 큐 적재·실서명 검증, `/deletions` CSRF).
- **eBay 알림 30일 기한을 코드가 지키게 만들기.** 방침 문서는 30일을 약속하지만, `pending` 행이
  승인 없이 30일을 넘겨도 아무 일도 일어나지 않는다(`/deletions` 의 대기 배지가 유일한 신호).
  기한 임박 건을 화면 상단에 띄우는 것이 방침과 동작을 실제로 일치시키는 마지막 조각이다.
- **처리 끝난 `pending_deletions` 행 정리.** 승인·기각 후에도 `status` 만 바뀌고 행은 남는다.
  `DATA_RETENTION` 경과분을 지우는 코드가 아직 없다 — 방침에 적은 파기 약속과 어긋난다.
- **격리 파일 보관 기간 정책.** 회전 상한(4MB/1MB)에 닿을 때까지 eBay userId 가 담긴 원본이 남는다.
  기간 기준 정리 작업을 붙이거나 상한을 줄여야 한다.
- 관리자 비밀번호가 실제로 무엇인지는 코드가 알 수 없다(3-3 의 경고는 "바꾼 적이 없다"까지만 말한다).
  MFA 가 들어가기 전까지는 사람이 주기적으로 확인하는 수밖에 없다.
- `proxy_logs` 테이블 + 관리 화면, 프록시 레이트리밋·동시성 제한(감사 §4-4).
- electron-builder **코드 서명** + `forceCodeSigning: true`, `asar: true` 복구(감사 §16).
  내부망 이동으로 노출은 줄었지만 서명 부재는 그대로 남아 있다.
- 관리자 로그인 MFA, DuckDNS → 회사 소유 도메인 이전.
- `login_logs` 인덱스 — 로그가 수십만 행이 되면 로그인 잠금 검사가 느려진다.
