# 상품 일괄 변경 처리 개선 (2026-10-01)

기존 아마존·eBay의 목록 캐시, 차량 카탈로그, 국내 기준가 환율 계산을 유지합니다.
상품 목록 동기화의 Reports API 대기 시간이나 쇼핑몰 자체 처리 시간은 이 변경으로 없어지지 않습니다.

## 변경 목록 처리

1. 화면에서 불러온 가격·이미지와 환율 계산 결과를 확인합니다.
2. 선택 변경 저장을 누르면 화면이 변경 목록을 한 번에 메인 프로세스로 전달합니다(`bulk-save-batch`).
3. 전체 입력 형식과 ESM 이미지 접근성을 먼저 검증하고 전송 계획을 로컬에 기록합니다.
4. 쇼핑몰별로 전송하고 행별 결과를 화면에 보냅니다. 반영 결과가 불명확하거나 인증·호출 제한 오류가 나면 남은 전송을 중단합니다.

같은 ESM URL은 한 작업 안에서 한 번만 확인합니다. 다음 작업에서는 다시 확인합니다.
현재가·이미지 불러오기는 동일 상품 API 응답을 공유합니다. 쿠팡 옵션별 현재가는 기존처럼 아이템별 가격 API로 확인합니다.
화면의 상품마다 550ms 조회 대기·650ms 저장 대기, 자동 환율 작업의 500ms 추가 대기를 제거했습니다.
각 API 클라이언트의 호출 제한과 전송 직전 가격·이미지 충돌 검사는 유지합니다.

## 현재가 묶음 조회 (2026-10-01)

현재가 불러오기는 상품마다 한 번씩 부르지 않고 몰이 한 요청에 허용하는 만큼 묶어 읽습니다(`bulk-price-load-many`).

- 네이버: 상품 목록 조회(`POST /v1/products/search`, `searchKeywordType: PRODUCT_NO` + `originProductNos`)로 100건씩 읽습니다. 100은 전체 목록 동기화가 실계정에서 쓰는 페이지 크기이며, 공식 최대값은 문서로 확인하지 못했습니다. 응답의 원상품번호로만 짝을 맞추고, 응답에 없는 번호는 원상품 1건 조회로 다시 읽습니다. 네이버가 이 조건을 400으로 거부하면 앱을 다시 켤 때까지 1건 조회로만 진행합니다.
- 네이버 묶음 결과에는 상세 이미지가 없어, 현재가·이미지 불러오기는 묶음으로 가격을 읽은 뒤 상품마다 이미지 목록을 읽습니다(2026-10-27). 화면은 진행 표시와 중단이 늦지 않게 10건씩 보냅니다. 이미지를 못 읽은 상품은 가격만 채우고 처리 결과 칸에 이유를 남깁니다. 환율 자동 변경은 가격만 읽어 100건 묶음 그대로입니다.
- 아마존: `searchListingsItems` identifiers 로 20건씩, 두 요청씩 보냅니다. 빠진 SKU 는 `getListingItem` 으로 읽습니다.
- 쿠팡(옵션별 가격 API)·eBay(SKU별 Offer)는 묶음 조회가 없어 지금처럼 상품마다 읽습니다. eBay 는 4건씩 동시에 읽습니다.
- 인증·호출 한도·프록시 오류가 나면 남은 상품을 조회하지 않고 멈춥니다.

네이버 일괄 저장은 판매가를 정해서 바꾸는 다건 API 가 없어(bulk-update 는 n원·n% 증감만, [공식 답변](https://github.com/commerce-api-naver/commerce-api/discussions/1669)) 상품마다 GET + PUT 입니다.
쓰기 뒤 확인만 10건씩 묶어 목록 조회 한 번으로 하고, 다르게 보이는 상품만 원상품 1건 조회로 확인합니다(상품당 GET 2회 + PUT 1회 → GET 1회 + PUT 1회 + 10건당 목록 조회 1회).
묶음 안에서도 중단과 결과 불명을 확인해, 그 뒤 상품은 보내지 않습니다.

## 쇼핑몰별 전송

- eBay 가격: 게시된 미국 USD Offer를 확인해 최대 25개씩 `bulk_update_price_quantity`로 전송합니다. 수량은 전송하지 않습니다. 응답은 SKU와 Offer ID로 대응하며 누락·중복 응답은 결과 불명으로 처리합니다. 성공 응답은 접수로 표시하고 후속 현재가 조회로 실제 반영을 확인합니다.
- 아마존 가격: 기존 Listings Items API를 유지합니다. 쓰기 직전 GET 한 번으로 현재가 충돌 검사와 기존 속성 보존을 함께 처리해 중복 GET을 제거했습니다.
- 네이버·쿠팡 가격 및 각 몰의 이미지: 기존 어댑터의 상품·옵션 단위 변경 경로를 사용합니다. 화면에서 한 번에 제출한다고 모든 쇼핑몰에 단일 HTTP 요청을 보내는 것은 아닙니다.
- 아임웹(B2B · 본사 한국/영문/일본, 2026-10-05~): Open API 로 상품마다 기본가 한 줄 + 조합마다 한 줄을 읽습니다(src/imweb_bulk.js).
  저장은 연속한 20줄씩 받아 같은 상품의 줄을 한 번 읽어 판단하고(불러온 뒤 바뀐 줄은 보내지 않음 · 같은 값은 '변경 없음'),
  바뀌는 줄만 보낸 뒤 한 번 다시 읽어 확인합니다 — 기본가 + 조합 3개가 12회 → 8회(2026-10-22). 중단은 상품 사이에서 멈춥니다.
  목록은 쪽 수를 알면 3쪽씩 동시에 읽습니다(본사 17쪽). 상세 이미지는 상세 영역 표시(본사 `<!--B .상세페이지-->`, B2B `<!--3. 상세페이지 영역-->`)
  뒤의 이미지만 바꿉니다 — 앞의 조견표 · 배너와 주석 속 옛 이미지는 그대로 둡니다(2026-10-21). 판매중이 아닌 상품은 이름 아래에 표시합니다.

아마존 Feeds는 비동기 처리 대기 시간이 추가되므로 이번 변경에서 전송 방식을 바꾸지 않았습니다.
[아마존 워크플로 문서](https://developer-docs.amazon/sp-api/docs/building-listings-management-workflows-guide),
[eBay 일괄 가격 변경 문서](https://developer.ebay.com/api-docs/sell/static/inventory/bulk-updates.html).

## 작업 기록과 중단

`userData/bulk_changes/<작업ID>.json`에 계획·최종 결과를 저장하고 `.jsonl`에 전송 직전/직후 진행 기록을 추가합니다.
기존 상품 DB 구조는 변경하지 않습니다. 같은 작업 ID를 다시 받으면 완료 결과를 돌려주며 다시 전송하지 않습니다.
앱 종료 등으로 RUNNING 기록만 남은 작업은 자동 재전송하지 않습니다. 현재가·이미지를 조회한 뒤 새 변경 작업을 만드세요.
중단 버튼은 현재 전송 중인 한 요청(eBay는 최대 25건)을 마친 뒤 남은 요청을 중단합니다.

새 메인 프로세스 IPC를 사용하므로 앱을 완전히 종료한 뒤 다시 실행해야 합니다.
운영 계정에 상품 변경을 보내지 않고 모의 API로 호출 수, 부분 실패, 중단, 재전송 방지와 화면 연결을 테스트했습니다.
